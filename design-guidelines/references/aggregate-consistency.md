# 集約と整合性の設計

整合性とは、ドメインモデルの複数部分が、業務上成立させるべき関係を満たしていることを指す。どの関係を、いつまでに成立させるかは業務要件として確認する。

集約とは、一つの整合性境界として更新し、原子的に保存するドメインオブジェクトのまとまりを指す。外部からの更新は集約ルートを通す。

## 1. 整合性の規則を具体化する

関連するデータの間で成立させる業務規則を明記する。その規則が破られた状態を具体例として示す。

例えば、注文の請求金額は全注文明細の合計と一致させる。明細の合計が3,000円で、請求金額が2,500円なら不整合である。

具体例を作ることで、何を同時に更新するか、何を導出値にするか、どこを集約境界にするかを判断できる。

## 2. 整合性が必要な期限を決める

業務規則をいつまでに成立させる必要があるかを明記する。一つの操作が完了する前に成立させるのか、一時的な不一致を許して後から成立させるのかを区別する。

- 注文明細と請求金額が、明細変更の完了時点で一致する必要があるなら、即時整合性を要求する。
- 注文確定後に請求書を作成する場合、業務が一時的な不一致を許せるなら、結果整合性を選択できる。

結果整合性を選ぶ場合は、「最終的に」の意味を時間で定義する。例えば「注文確定から10分以内」と定める。この10分は説明用であり、実際の期限は業務要件として確認する。

## 3. 集約内の整合性を設計する

元データから導出できる値は、保持せず必要時に計算することを優先する。

```ts
type Order = Readonly<{
  lines: readonly OrderLine[];
}>;

const amountToBill = (order: Order): Money =>
  sumLinePrices(order.lines);
```

導出値を保持する必要がある場合は、元データと同じ集約に含める。集約ルートの操作で、元データと導出値を同時に更新する。子要素だけを外部から直接更新させない。

集約全体を一つの原子的な永続化単位として保存する。集約の一部だけが保存された状態を、正常な状態として読み出させない。

## 4. 境界づけられたコンテキスト間の整合性を設計する

別の境界づけられたコンテキストの内部データを直接変更しない。ドメインイベントによって、相手側の処理を開始する。

```ts
type PlaceOrderOutcome = Readonly<{
  order: Order;
  events: readonly [OrderPlaced];
}>;
```

イベントを型に含めても、配送成功までは保証できない。メッセージが失われた場合は、次のいずれかを業務上の損失に応じて選ぶ。

- 不一致を受け入れる。
- データを照合し、不足する処理を再実行する。
- 以前の処理を取り消すか、影響を修正する補償処理を行う。

結果整合性は、整合性を任意にすることではない。定義した期限までに、定義した状態へ収束させる。

## 5. 同じコンテキスト内の複数集約を扱う

原則として、一つのトランザクションでは一つの集約を更新する。集約をまたぐ変更には、ドメインイベントと結果整合性を検討する。

業務が一つの原子的な処理として扱う場合は、複数の対象を同じトランザクションへ含める判断もあり得る。その場合は、次の可能性を先に検討する。

- 集約境界が実際の整合性境界と一致していない。
- 複数集約にまたがる処理自体が、独立した業務概念である。

送金に送金識別子とライフサイクルがあるなら、二つの口座を更新する処理だけでなく、送金というエンティティまたは集約を設計する。

## 6. 発展的な実装確認

次の項目は、書籍の整合性の議論を実運用へ進める際の追加確認である。

- 再試行によって同じ変更を重複適用しないようにする。
- メッセージの消失と処理漏れを検出できるようにする。
- メッセージの順序が変わっても、業務規則を破らないようにする。
- 同時更新による競合を検出し、再試行または拒否できるようにする。
- 集約の更新とイベントの記録が片方だけ成功しないようにする。
- 結果整合性が期限内に収束しているか観測できるようにする。

具体的な実装方式は、データストア、メッセージ基盤、障害時の損失によって選ぶ。方式名を先に決めず、必要な保証から選択する。

## レビュー項目

- 成立させる業務規則と、不整合の具体例が明確か。
- 即時整合性が必要な範囲と、その業務上の理由が明確か。
- 導出可能な値を不要に重複保持していないか。
- 集約ルートを通さず、子要素を更新できないか。
- 集約境界と原子的に保存する範囲が一致しているか。
- 複数集約を同じトランザクションで変更する理由があるか。
- 結果整合性が収束する期限と責任主体が定義されているか。
- メッセージの消失、重複、順序変更を扱えるか。
- 照合処理または補償処理が必要か。
- 複数集約の同時更新が、新しい業務概念の存在を示していないか。
