# Type Guidelines

## 目的

業務上の不変条件を明らかにし、型で強制できる規則と実行時に保証する規則を分ける。実装時には不正な状態を作りにくくし、レビュー時には不変条件を迂回できる経路を特定する。

## 基本方針

- 業務規則を確認してから型を選ぶ。
- 外部から入る未検証のデータと、内部の検証済みデータを区別する。
- 型で強制できない規則を、型で保証したと報告しない。
- データベースや通信形式に合わせて、ドメインモデルを歪めない。
- 実装を求められていないレビューでは、コードを変更せず指摘と改善案を提示する。

## 参照先の選択

依頼に必要な参照ファイルだけを全文読む。複数の論点を含む場合は、該当する参照ファイルをすべて読む。

- 数値範囲、文字列形式、識別子、金額、単位、スマートコンストラクタを扱う場合は、[references/integrity.md](references/integrity.md)を読む。
- AND条件、OR条件、条件付き必須項目、検証前後の状態、状態遷移を扱う場合は、[references/states.md](references/states.md)を読む。
- 複数データをまとめる集約型、整合性を保つ公開関数、独立したエンティティ型、複数集約で共有する制約付き型を扱う場合は、[references/aggrigate.md](references/aggrigate.md)を読む。

## 作業手順

1. 対象となる業務規則を、不正となる具体例とともに列挙する。
2. 各規則が単一値、複合状態、複数データ間の整合性のどれに属するか分類する。
3. 該当する参照ファイルを読み、型と更新境界を設計する。
4. 生成、更新、復元、直列化、永続化の各経路から不変条件を迂回できないか確認する。
5. 型で保証する範囲と、実行時の検証が必要な範囲を明記する。

## レビュー結果

各指摘に次の内容を含める。

- 守るべき業務規則
- 問題が確認できるコード上の根拠
- 表現または発生できる不正状態
- 推奨する最小限の変更
- 変更後も実行時の保証が必要な範囲

問題がない場合も、確認した生成経路と更新経路を簡潔に示す。
