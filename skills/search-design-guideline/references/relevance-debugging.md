# 検索関連性の技術デバッグ

特定の検索語について、期待した文書が検索結果に含まれない理由、無関係な文書が含まれる理由、または期待した文書の順位が低い理由を調査する。

この文書では、マッチングを「文書を検索結果の候補に含めるかを決める処理」、ランキングを「候補に含まれた文書の表示順を決める処理」と定義する。最初に両者を切り分け、原因を示す証拠を得てから変更案を選ぶ。

検索システム全体から改善課題を発見する活動、複数の課題の優先順位付け、利用者調査、検索画面の評価は、この文書の対象外とする。

## 1. 調査に必要な情報を固定する

調査を始める前に、次の情報を記録する。

- 利用者が入力した検索語
- アプリケーションが検索エンジンへ送った実際のクエリ
- 検索対象の索引またはエイリアス
- 期待した文書の識別子と、期待する順位または表示条件
- 実際に返された文書、順位、スコア
- 適用されたフィルター、権限制御、並べ替え
- 文書モデル、フィールド定義、解析器、辞書の版
- 調査に使用した索引の版または作成時刻

画面上の検索語だけから原因を推測しない。アプリケーションが検索語を書き換えたり、フィルターや複数の検索条件を追加したりする場合があるため、検索エンジンが実際に受け取ったクエリを保存する。

同じ索引、同じクエリ、同じ文書を使って問題を再現できない場合は、原因を確定しない。再現できない事実と不足している情報を報告する。

## 2. 検索関連性以外の原因を先に除外する

マッチングとランキングを調べる前に、次を確認する。

- 期待した文書が検索対象の索引に存在する。
- アプリケーションが意図した索引またはエイリアスを参照している。
- 文書の追加、更新、削除が索引へ反映されている。
- 権限制御、状態、期間、在庫などのフィルターが文書を除外していない。
- 明示的な並べ替えが検索スコアによる順位を上書きしていない。
- 検索処理が失敗した結果として、代替結果やキャッシュ済み結果を返していない。

この確認で原因が見つかった場合は、検索関連性の調整へ進まない。データ登録、権限制御、運用、またはアプリケーションの問題として記録する。

## 3. マッチングとランキングを切り分ける

期待した文書が候補集合に含まれるかを確認する。候補集合とは、表示件数の上限で切り捨てる前に、クエリの一致条件を満たした文書の集合である。

- 期待した文書が候補集合に含まれない場合は、マッチングを調べる。
- 無関係な文書が、価値の低い語への一致だけで候補集合に含まれる場合も、マッチングを調べる。
- 期待した文書が候補集合に含まれるが順位が低い場合は、ランキングを調べる。
- 文書が一致する理由と順位が高い理由の両方に疑問がある場合は、マッチングを先に調べる。

検索結果の先頭に文書が見えないことだけを根拠に、マッチングの失敗と判定しない。取得件数を増やす、文書識別子を指定して一致判定を確認するなどの方法で、候補集合への包含を確認する。

## 4. マッチングを調べる

### 4.1 実行されるクエリを確認する

利用者の入力ではなく、検索エンジンが解釈したクエリを確認する。少なくとも次を記録する。

- 検索対象のフィールド
- `MUST`、`SHOULD`、`MUST_NOT`などの論理条件
- 最低一致数、フレーズ条件、近接条件
- フィルターと除外条件
- フィールドごとの検索語
- 複数の部分クエリを結合する方法
- クエリ時の解析器

想定していないフィールド、条件、検索語が含まれている場合は、クエリ生成処理を原因候補とする。解析器を変更する前に、クエリ構造の誤りを除外する。

### 4.2 検索語と文書を別々に解析する

検索時の解析結果と索引作成時の解析結果を別々に取得する。各トークンについて、文字列、位置、開始位置、終了位置を比較する。

次を確認する。

- 大文字と小文字、全角と半角、Unicode正規化などの表記が統一されている。
- 活用形、単数形と複数形、送り仮名などが期待どおりに正規化されている。
- 助詞、前置詞など、検索意図を表しにくい語が不要な一致を生んでいない。
- 同義語や複合語の展開が、検索時と索引作成時で矛盾していない。
- フレーズ検索に必要なトークン位置が保持されている。
- 検索時と索引作成時で、同じ概念が同じトークンになっている。

解析APIは、指定したテキストへ解析器を適用した結果を返す。解析APIの結果を、既存文書から読み出した索引語だと解釈しない。既存文書について実際の語、出現回数、位置を確認する必要がある場合は、使用中の検索製品が提供するタームベクター相当の機能を使う。

### 4.3 クエリの語と索引の語を対応させる

クエリの各語について、同じフィールドに同じ索引語が存在するかを確認する。文字列が一致していても、フィールドが異なる場合は一致しない。

期待した文書が含まれない場合は、次の順序で原因を絞る。

1. クエリが期待したフィールドを検索しているか。
2. 検索語が期待したトークンへ変換されているか。
3. 文書が索引作成時に期待したトークンへ変換されているか。
4. 必須条件、フレーズ条件、最低一致数を満たしているか。
5. 解析器または辞書を変更した後、対象文書を再索引したか。

無関係な文書が含まれる場合は、どの語が一致を成立させたかを特定する。価値の低い語が原因でも、その語を直ちに削除しない。他の検索例で必要な語ではないかを確認し、変更による再現率の低下を評価する。

### 4.4 デフォルトの解析器を無検証で採用しない

デフォルトの解析器が不適切だと決めつけない。対象言語、フィールド、利用者の検索語に対して、生成されるトークンを確認する。

解析器または辞書の変更が必要な場合は、次を明示する。

- 変更対象のフィールド
- 索引作成時と検索時のどちらを変更するか
- 追加または削除されるトークン
- 改善する検索例
- 悪化する可能性がある検索例
- 再索引の要否

## 5. ランキングを調べる

### 5.1 比較する文書を選ぶ

少なくとも次の2文書を、同じクエリと同じ索引で比較する。

- 本来上位に置きたい文書
- 現在その文書より上位にある文書

上位文書だけを説明しても、順位差の原因は分からない。両方のスコア説明を取得し、どの部分クエリ、フィールド、検索語が差を作ったかを比較する。

### 5.2 スコア説明を外側から読む

スコア説明は、次の順序で確認する。

1. 文書全体のスコアを結合する方法
2. 部分クエリを加算、最大値、乗算などで結合する方法
3. フィールドごとの寄与
4. 検索語ごとの寄与
5. 語の出現回数、文書集合内での希少性、フィールド長などの統計
6. ブーストや関数による補正

スコア計算方式を確認してから内訳を読む。Relevant Search第3章の例は、LuceneのClassic SimilarityによるTF、IDF、fieldNormを中心に説明している。使用中の検索システムが別のスコア計算方式を使う場合は、同じ構成要素が現れるとは限らない。

説明に現れた数値を、そのまま利用者にとっての重要度と解釈しない。数値がどの統計と結合規則から生じたかを確認する。

### 5.3 ブーストを優先順位そのものとして扱わない

ブーストは、既に計算されたスコアへ作用する補正係数である。`title^10`と指定しても、タイトル一致が本文一致より常に10倍重要になるとは限らない。

フィールド間では、文書の長さ、語の分布、索引中の文書数、スコア計算方式が異なる。そのため、同じ品質の一致でもスコアの尺度が大きく異なる場合がある。

ブーストを決めるときは、次の順序を守る。

1. 代表的な検索例で、各フィールドのスコア範囲を確認する。
2. フィールド間のスコア尺度を補正する。
3. 補正後の状態で、利用者または事業上の優先度を反映する。
4. 単一の成功例ではなく、回帰評価集合で副作用を確認する。

大きいブーストを付けることだけを改善案にしない。必要であれば、あるフィールドのブーストを1未満にして寄与を下げる。

### 5.4 スコアの絶対値を品質判定に使わない

検索スコアは、検索語、検索対象フィールド、語の分布、索引内容、スコア計算方式によって尺度が変わる。異なる検索語や異なるフィールドのスコアを、そのまま比較しない。

「スコアが2.0以上なら表示する」のような固定閾値を導入しない。固定閾値が必要な要件では、対象となる検索語の分布、索引の更新、設定変更に対して閾値が安定することを評価データで確認する。確認できない場合は、順位、取得件数、別の判定モデルなどを検討する。

## 6. 製品固有のデバッグ機能を対応づける

次の表はElasticsearchの例である。実行前に、使用中の製品と版の公式資料で、API、権限、本番環境への負荷を確認する。

| 調べる対象 | Elasticsearchの機能例 | 解釈上の注意 |
| --- | --- | --- |
| 実行されるクエリ | Validate Query API: `POST /{index}/_validate/query?rewrite=true` | 現行資料では、実行されるLuceneクエリの詳細確認に`rewrite=true`を使用する。入力が有効であることだけで、意図した検索になるとは限らない。 |
| 入力テキストの解析結果 | Analyze API: `POST /{index}/_analyze` | `field`または`analyzer`を明示する。既存文書の索引語を読み出す機能ではない。 |
| 既存文書の語と統計 | Term Vectors API: `POST /{index}/_termvectors/{id}` | 語、出現回数、位置などを確認する。統計値の範囲や正確性に製品上の制約があるため、絶対値として扱わない。 |
| 特定文書の一致とスコア | Explain API: `POST /{index}/_explain/{id}` | 比較対象の文書へ同じクエリを適用し、説明木の同じ階層を比較する。複数の検索結果を一度に確認する場合は、Search APIのリクエスト本文で`"explain": true`を指定できる。 |

製品固有の出力項目名を、一般的な設計概念だとみなさない。別の検索製品では、同じ調査を異なる機能で行う。

## 7. 原因に対応する最小の変更を選ぶ

確認した原因と変更対象を一致させる。

| 確認した原因 | 変更対象の例 |
| --- | --- |
| アプリケーションが誤ったフィールドや論理条件を生成している | クエリ生成処理 |
| 検索時と索引作成時のトークンが一致しない | 解析器、辞書、フィールド定義 |
| 価値の低い語が不要な一致を生んでいる | ストップワード、クエリ条件 |
| フレーズまたは語順の条件が意図と異なる | トークン位置、フレーズ条件、近接条件 |
| 複数フィールドのスコア尺度が異なる | フィールド構成、結合方法、ブースト |
| 一部の語の統計が順位を過度に支配している | スコア計算方式、フィールド分割、クエリ構造 |

診断結果だけから、解析器、クエリ、ブーストを同時に変更しない。複数箇所を同時に変更すると、どの変更が結果へ影響したかを確認できない。

## 8. 変更を評価する

修正前に、問題を再現する検索例を回帰評価集合へ追加する。最低でも次を含める。

- 元の問題を再現する検索例
- 同じ解析器またはフィールドを使う代表的な検索例
- 変更によって悪化し得る検索例
- ゼロ件検索と過剰一致を確認する検索例

変更後は、次を確認する。

1. 原因として特定したクエリ、トークン、またはスコア寄与が意図どおり変化した。
2. 期待した文書の包含または順位が改善した。
3. 既存の重要な検索例を悪化させていない。
4. 解析器または索引設定を変更した場合、必要な再索引を実施した。
5. 使用したクエリ、索引、設定、評価集合の版を記録した。

単一の検索例が改善したことだけで完了としない。

## 9. 調査結果の出力

次の順序で報告する。

1. **再現条件**: 検索語、実際のクエリ、索引、対象文書、期待結果、実結果
2. **切り分け**: マッチング、ランキング、または検索関連性以外の問題
3. **確認済みの事実**: クエリ、トークン、索引語、スコア説明から確認した内容
4. **原因**: どの処理が、どのように期待と異なったか
5. **最小の変更案**: 原因へ直接対応する変更
6. **回帰確認**: 改善した検索例と悪化していない検索例
7. **残る不確実性**: 未確認の仮説、取得できなかった情報、運用上の制約

原因を確認できていない場合は、推測を原因として報告しない。「未確認の仮説」として、確認に必要な追加情報または実験を示す。

## 10. レビュー項目

- 画面上の検索語ではなく、検索エンジンへ送ったクエリを確認したか。
- 検索関連性以外の原因を除外したか。
- マッチングとランキングを切り分けたか。
- 検索時と索引作成時の解析結果を別々に確認したか。
- 解析APIの結果を、既存文書から読み出した索引語だと誤認していないか。
- 上位文書と期待した文書のスコア説明を比較したか。
- 使用中のスコア計算方式を確認したか。
- ブーストをフィールドの優先度そのものとして扱っていないか。
- 異なる検索語またはフィールドのスコアを絶対値で比較していないか。
- 原因を示す証拠と、変更対象が対応しているか。
- 一度に複数の原因候補を変更していないか。
- 元の問題と副作用を回帰評価集合で確認したか。

## 典拠と版に関する注意

この文書の中核となる切り分けと調査手順は、Doug Turnbull、John Berryman『Relevant Search』第3章「Debugging your first relevance problem」に基づく。同章の製品例は2016年当時のElasticsearch 2.0とLuceneのClassic Similarityを使用しているため、API構文と既定のスコア計算方式を現在の実装へそのまま適用しない。

製品固有の機能は、次の公式資料で現在の仕様を確認する。

- [Validate a query](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-validate.html)
- [Get tokens from text analysis](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-indices-analyze)
- [Get term vector information](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-termvectors)
- [Explain a document match result](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-explain)
- [Run a search](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-search)
