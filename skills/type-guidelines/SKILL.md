# Type Guidelines

## 目的

業務上の不変条件を明らかにし、型で強制できる規則と実行時に保証する規則を分ける。実装時には不正な状態を作りにくくし、レビュー時には不変条件を迂回できる経路を特定する。

型定義は、業務規則を読み取れる記述でもある。ドメインの名詞は制約付きの値と状態として、動詞はワークフローの関数として表す。型を変更すると実装がコンパイルに失敗するため、設計と実装が乖離しない。

## 基本方針

- 業務規則を確認してから型を選ぶ。
- ドメインの名詞と動詞の両方を型で表す。名詞だけを整えても、処理が例外と隠れた依存のままなら不正な挙動は残る。
- 外部から入る未検証のデータと、内部の検証済みデータを区別する。
- 型で強制できない規則を、型で保証したと報告しない。
- データベースや通信形式に合わせて、ドメインモデルを歪めない。
- 型名とフィールド名に、業務で使われている語を使う。`Manager`、`Handler`、`Info`、`Data`のような、業務に存在しない語で型を作らない。
- スキーマ検証ライブラリ（zod、Pydantic）は、境界での検証と型の生成を同時に行う手段として使う。ライブラリを使っても、検証を迂回できる経路が残ることを前提に確認する。
- 実装を求められていないレビューでは、コードを変更せず指摘と改善案を提示する。

## 前提とする実装方式

例と指摘は次の方式を前提とする。これ以外の言語や構成の場合は、
同じ設計で保証できる範囲が変わるため、保証範囲を明示してから提案する。

- TypeScript。境界の検証にzod、想定内の失敗に結果型（`Result`または`Either`）を用いる。
- Python。境界の検証にPydanticを用いる。

## 参照先の選択

依頼に必要な参照ファイルだけを全文読む。複数の論点を含む場合は、該当する参照ファイルをすべて読む。

- 既存のコードをレビューする場合は、最初に[references/smells.md](references/smells.md)を読み、徴候から論点を特定する。
- 数値範囲、文字列形式、識別子、金額、単位、スマートコンストラクタを扱う場合は、[references/integrity.md](references/integrity.md)を読む。
- AND条件、OR条件、条件付き必須項目、検証前後の状態、状態遷移を扱う場合は、[references/states.md](references/states.md)を読む。
- 複数データをまとめる集約型、整合性を保つ公開関数、独立したエンティティ型、複数集約で共有する制約付き型を扱う場合は、[references/aggrigate.md](references/aggrigate.md)を読む。
- ユースケースの入力型、出力型、エラー型、処理段階の分割、依存関係の注入を扱う場合は、[references/usecase.md](references/usecase.md)を読む。
- 値オブジェクトとエンティティの区別、等値性、更新関数の形を扱う場合は、[references/identity.md](references/identity.md)を読む。
- 型にしない判断、既存コードへの段階的な適用順序を扱う場合は、[references/limits.md](references/limits.md)を読む。

## 作業手順

1. 型名とフィールド名が業務の語になっているか確認する。業務の語が不明な場合は推測せず、確認事項として記録する。
2. 対象となる業務規則を、不正となる具体例とともに列挙する。
3. 各規則が単一値、複合状態、複数データ間の整合性、ワークフローの入出力のどれに属するか分類する。
4. 該当する参照ファイルを読み、型と更新境界を設計する。
5. 型が表現できる状態の数と、業務上妥当な状態の数を比較する。差がある場合、その差が不正な状態である。
6. 生成、更新、復元、直列化、永続化の各経路から不変条件を迂回できないか確認する。
7. 型で保証する範囲と、実行時の検証が必要な範囲を明記する。

## レビュー結果

各指摘に次の内容を含める。

- 守るべき業務規則
- 問題が確認できるコード上の根拠
- 表現または発生できる不正状態
- 推奨する最小限の変更
- 変更後も実行時の保証が必要な範囲

指摘は多くても6件に絞り、効果の大きい順に並べる。段階的に適用できる場合は、[references/limits.md](references/limits.md)の順序に従って優先度を示す。

確認済みの業務規則と、未確認の仮説を区別して記載する。業務規則を推測で断定しない。

問題がない場合も、確認した生成経路と更新経路を簡潔に示す。
