# 値オブジェクトとエンティティの区別

同じデータでも、等しさの判定方法によって型の設計と更新方法が変わる。
この区別を決めないまま型を書くと、等値比較と更新関数の設計が場当たりになる。

## 判定

判定質問は「構成要素が変わっても、それは同じものか」である。

| | 値オブジェクト | エンティティ |
| --- | --- | --- |
| 等しさ | 構成要素がすべて等しければ等しい | 識別子が等しければ等しい |
| 例 | 製品コード、個人名、住所、金額 | 注文、顧客、製品、送金 |
| 一部を変更 | 別の値になる。更新の概念がない | 同じものの状態が変わる |
| 型の構成 | 識別子を持たない | 識別子を持つ |

「クリスは私と同じ名前を持っている」と言えるなら、名前は値オブジェクトである。
名前自体が固有の identity を持っていない。

## 設計手順

1. 対象が永続的な識別子を持つか確認する。
2. 値オブジェクトは識別子を持たせず、構成要素による等値比較にする。
3. エンティティは識別子だけで等値比較する。
4. どちらも作成後の値を不変にする。
5. エンティティの更新は、識別子を維持した新しい値を返す関数として定義する。

## ガイドライン

- 言語が提供する既定の等値比較が、構成要素の比較かを確認する。
- 構成要素の比較が既定である言語では、**エンティティに既定の比較を使わない**。
  名前を変更した人物が別人として扱われる。
- 値オブジェクトを、識別子を付けてエンティティに昇格させる前に、
  業務上の identity が存在するか確認する。
- 更新関数が`void`を返す設計にしない。何が変わったかを型が示さなくなる。
- 集約の内部でエンティティを更新する場合も、集約全体を返す
  （[aggrigate.md](aggrigate.md)の公開関数の規則に従う）。

## TypeScriptによる例

値オブジェクトは構成要素で比較する。

```ts
type PersonalName = Readonly<{
  firstName: String50;
  lastName: String50;
}>;

const equalsName = (a: PersonalName, b: PersonalName): boolean =>
  a.firstName.value === b.firstName.value &&
  a.lastName.value === b.lastName.value;
```

エンティティは識別子で比較し、更新は識別子を維持した新しい値を返す。

```ts
type Person = Readonly<{
  id: PersonId;
  name: PersonalName;
}>;

const equalsPerson = (a: Person, b: Person): boolean =>
  a.id.value === b.id.value;

const renamePerson = (person: Person, name: PersonalName): Person => ({
  ...person,
  name,
});
```

次のシグネチャは使わない。出力がないため、何も変化しないか、
引数を直接変更していることになる。

```ts
type RenamePerson = (person: Person, name: PersonalName) => void;
```

## レビュー項目

- 値オブジェクトに、業務上必要のない識別子が付いていないか。
- エンティティの等値比較が、識別子以外のフィールドに依存していないか。
- 構成要素の比較を既定とする型を、エンティティに使っていないか。
- 更新関数が`void`を返し、引数を直接変更していないか。
- 集約に属するエンティティを、集約を経ずに更新できないか。

## 型だけでは保証できない範囲

識別子の一意性は型では保証しない。生成規則、永続化層の制約、
または重複検出で保証する。
