# モデル選定の評価基準

## 目的

用途の要求を、候補を除外または比較できる評価基準へ変換する。測りやすい指標だけを選ばず、利用者が得たい成果と、失敗時の影響から基準を導く。

## 必須条件と改善可能な評価項目

最初に各条件を次のいずれかへ分類する。

- 必須条件: 満たさない候補を除外する。例として、データを指定地域から出さないこと、商用利用が許可されること、応答時間の上限があることが該当する。
- 改善可能な評価項目: プロンプト、検索処理、追加学習、推論最適化によって改善できる可能性がある。例として、正確性、指示追従、安全性、コストが該当する。

同じ条件でも、利用方式によって分類が変わる。外部のモデルAPIを使う場合、モデル自体のレイテンシや機能は変更しにくい。自社運用では最適化できる可能性があるが、必要な期間と費用を見積もる。

## 評価基準の分類

### 1. 領域固有の能力

対象業務に必要な知識と処理能力を評価する。

- 分類では、正解率、適合率、再現率、F1値を検討する。
- プログラムや構造化クエリでは、機能的な正しさに加えて、実行時間、メモリ使用量、保守性を検討する。
- 検索や外部ツールを使うタスクでは、モデル単体の能力と、システム全体のタスク完了率を分ける。
- 複数回の対話が必要な場合は、各応答の品質だけでなく、タスク完了率、完了までの対話回数、途中離脱率を測る。

### 2. 生成品質

自由形式の出力に求める性質を分解する。一つの「品質」点にまとめて定義しない。

- 関連性: 利用者の質問と目的に応えているか。
- 局所的な事実整合性: 与えた文書、検索結果、業務データによって出力を裏付けられるか。
- 大域的な事実整合性: 信頼できる外部情報と矛盾しないか。使用した情報源と確認時点を記録する。
- 完全性: 必要な論点を欠いていないか。
- 安全性: 有害な助言、差別、機密情報の露出など、用途で想定する害を避けているか。
- 文体と可読性: 対象読者、媒体、専門性に合っているか。

正解を機械的に判定できない項目には、採点基準と具体例を用意する。AIによる評価を使う場合も、人間が採点基準に合意できることを先に確認する。

### 3. 指示追従能力

内容を理解する能力と、指定された制約を守る能力を分ける。内容が正しくても、後続処理が要求する形式に従わなければ失敗として扱う。

- JSONやスキーマへの適合
- 許可された選択肢だけを出力すること
- 長さ、段落数、必須語、禁止語
- 対象言語、口調、対象読者
- 対象外の依頼を拒否すること
- 役割を維持し、役割が知り得ない情報を述べないこと

形式、語数、選択肢などは決定的なプログラムで検査する。意味、口調、役割の一貫性などは、採点基準に基づく人間またはAIの評価を使う。

### 4. コスト、レイテンシ、処理能力

実際の入力長、出力長、同時実行数を使って測定する。

- 1タスク当たりの総費用
- 入力および出力100万トークン当たりの料金
- 最初のトークンが返るまでの時間
- 応答全体が完了するまでの時間
- 50、90、99パーセンタイルのレイテンシ
- 1分当たりのトークン数、要求数、同時実行数
- 再試行、検索、外部ツール、評価処理を含むシステム全体の費用

平均値だけで判断しない。利用者が体験する上位パーセンタイルと、負荷が高い時間帯を確認する。

### 5. 運用上の制約

品質評価の前に、候補を除外する条件として扱う場合が多い。

- データの保存、学習利用、保管地域
- ライセンスと商用利用条件
- 必要な入出力モダリティ、構造化出力、外部ツール連携
- コンテキスト長、要求の上限、利用制限
- 監査ログ、版の固定、廃止通知、サービス水準
- 監視、障害対応、追加学習、推論最適化に必要な人員

## 評価表の作り方

各行を一つの評価基準とし、次の列を持つ表を作る。

| 列 | 記録する内容 |
| --- | --- |
| 基準 | 一意に判定できる評価項目 |
| 理由 | 利用者または事業上の必要性 |
| 測定対象 | 構成要素、応答、対話、タスク全体のいずれか |
| 指標 | 測定値と、値が良くなる方向 |
| 方法 | 自動検査、専用判定器、AIによる評価、人間による評価 |
| データ | 代表例、既知の失敗、境界条件などの評価集合 |
| 必須値 | 満たさない候補を除外する境界 |
| 目標値 | 採用後に目指す値 |
| 根拠 | 必須値と目標値を決めた業務上の理由 |

必須値を決められない場合は、暫定値を事実として扱わない。試験運用で利用者の成果や事業指標との関係を確認する計画を示す。

## 評価データ

一つの評価セットだけで全てを判断しない。次の集合を必要に応じて分ける。

- 実運用の入力分布を代表する集合
- 重大な失敗につながる入力の集合
- 過去に失敗した入力の回帰確認用集合
- 長文、誤字、少数言語など、性能差を確認するデータ区分
- システムが応答すべきでない対象外入力の集合

全体値とデータ区分ごとの値を併記する。全体値が改善しても、重要な利用者群や重大な失敗の性能が低下していないか確認する。

評価件数を端数のない経験値だけで決めない。候補間で検出したい最小の差、必要な信頼度、指標の分散を使って見積もる。重大事故のように発生率を上限で管理する場合は、観測が0件でも真の発生率が0であるとは扱わず、許容上限を示すために必要な件数を求める。分散や発生率が不明な場合は、予備評価を行い、再標本化によって結果の安定性を確認してから本評価の件数を決める。

## 複数目的の扱い

必須条件を満たした候補だけを比較する。品質、費用、レイテンシのいずれかを改善すると他が悪化する場合は、どの候補も一律に優れていると報告しない。

総合点を使う場合は、次の内容を明記する。

- 異なる単位の指標をそろえる正規化方法
- 各指標の重みと、その根拠
- 欠損値の扱い
- 重みを変更した感度分析

総合点だけでなく、元の測定値と、候補ごとの弱点を残す。
