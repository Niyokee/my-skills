# システム価値

## 目的

システム価値とは、対象システムに関わる人・組織と外部システムを要求の源泉として把握し、システムの目的・役割と、実現すべき要件を明らかにする視点である。金額だけを扱うものではない。

この段階では、誰にとって何が改善されればよいかだけで終わらせない。対象システムの目的・役割、関係する役割（アクター）、外部システム、および各アクターが持つ要望・要求・要件を関係付ける。

## 反復の管理

各回の作業を反復として扱い、後述のチェックリストを複製して進捗を管理する。チェック欄は次のように使う。

- `[x]`: 今回の反復で確認できた項目
- `[ ]`: まだ確認できていない項目
- `[ ] （今回スキップ: 理由）`: 意図的に次回以降へ送る項目

1st iterationでは、関係者の暗黙知や対象範囲の理解が十分でない場合がある。前提となる項目を確認できていないときは、後続の項目をスキップしてよい。推測でチェックを付けず、スキップした理由、追加で話を聞く相手、次に確認する質問を記録する。次の反復では、前回スキップした項目を未確認のチェック欄として引き継ぐ。

インタビューでは、関係者から回答を得るたびにチェックリストを更新する。次の質問をする前に、確認できた項目、未確認の項目、今回スキップする項目を関係者に示す。

## 最終成果物

RDRAとしての中心成果物は、次の二つのモデルである。

ここで示す最終成果物は、全ての反復を通した到達目標である。1st iterationで全てを完成させる必要はない。反復中の成果物では、確認できた範囲だけを記述し、仮説、未確認、今回スキップを明示する。

1. **コンテキストモデル**: 対象システムの目的・役割、アクター、外部システムを表す。ここでいうアクターは個人名ではなく、対象業務に必要な役割を表す。以降のモデルで同じアクターを再利用する。この文書群では、コンテキストモデルを「システムコンテキスト」とも呼ぶ。
2. **要求モデル**: コンテキストモデルのアクターを発言者として、要望・要求・要件を構造化して表す。要件は機能要求と非機能要求に分類し、必要に応じてそれぞれをサブモデルとして表す。

次の二つは、RDRAの中心モデルを補強するための補助成果物である。モデルそのものの代わりにはしない。

- **システム価値の要約文**: システムの目的・役割を一文で表す。コンテキストモデルに記載し、関係者と確認する。
- **追跡表**: アクター、要望、要求、要件、後続のビジネスユースケース（BUC）・ユースケース（UC）を識別子で対応付ける。根拠、確度、優先度、未解決事項もここで管理する。

## 作成手順

チェックリストは上から順に進める。ただし、理解が不十分な場合は後続の項目をスキップし、前の項目に戻ってインタビューを続ける。

### 1. システムに関わる人を把握する

- [ ] 対象業務、対象システム、暫定的な対象外を確認する。
- [ ] システムを直接利用する人を、個人名ではなく役割の単位で洗い出す。
- [ ] システムを直接利用しなくても、業務上の影響を受ける人、運用または支援を担う人、規則を定める人、要求の決定権を持つ人を洗い出す。
- [ ] 各役割の責務、対象システムとの関係、影響力または決定権を記録する。
- [ ] 見落としている関係者がいないかを、把握済みの関係者に確認する。

### 2. システムに関わる外部システムを把握する

- [ ] 対象システムと情報または出来事をやり取りする外部システムを洗い出す。
- [ ] 各外部システムについて、対象システムとの関係、やり取りの目的、情報の向きを記録する。
- [ ] 現在は人手で仲介しているやり取りについても、情報の出所または提供先となる外部システムがないかを確認する。
- [ ] この段階では具体的なインターフェース仕様を決めない。

### 3. コンテキストモデルで整理する

- [ ] 対象システム、関係する役割、外部システム、および相互の関係をコンテキストモデルに配置する。
- [ ] 関係する役割と外部システムを踏まえ、対象システムの役割を一文で記述する。
- [ ] 対象システムによって達成したい目的を一文で記述する。
- [ ] システムの役割、目的、対象範囲、対象外を関係者に確認する。

### 4. システムに関わる人のシステムへの要望をまとめる

- [ ] コンテキストモデルに配置した各役割から、システムに対する要望を聞く。
- [ ] 要望の発言を、発言者、具体的な状況、背景とともに記録する。
- [ ] 同じ要望を持つ役割、相反する要望を持つ役割、まだ要望を確認できていない役割を明示する。
- [ ] 画面、API、製品名などの解決策を、要望そのものと分けて記録する。

### 5. 問題・課題から本質的な要求・要件を明らかにする

- [ ] 各要望について、現在起きている問題、解決すべき課題、問題が生じる具体的な状況を確認する。
- [ ] 「なぜ必要か」「解決しないと誰がどのように困るか」を尋ね、要望の背後にある意図を確認する。
- [ ] 要望を具体化、抽象化し、依存関係を整理して、解決の方向性を要求として記録する。
- [ ] 実現すべき重要な項目を要件として選び、機能要求または非機能要求に分類する。
- [ ] 要望、問題・課題、要求、要件の関係を根拠とともに追跡できるようにする。
- [ ] 相反、重複、優先度、未確定事項を明示する。

### 6. 要求モデルと後続モデルへつなぐ

- [ ] 要望、要求、要件を発言者である役割に対応付けた要求モデルを作成する。
- [ ] 要件から後続のビジネスユースケース（BUC）・ユースケース（UC）まで追跡できるようにする。

## モデルの内容

### コンテキストモデル

コンテキストモデルには、少なくとも次を含める。

- 対象システム
- システムの目的・役割
- アクターと各アクターの責務
- 外部システム
- アクターまたは外部システムと対象システムとの関係

アクターの選定が不十分だと、システム化の範囲が変わる。関係者とのレビューでは、利用者だけでなく、影響を受ける人と要求の決定権を持つ人が含まれているかを確認する。

### 要求モデル

要求モデルでは、同じ内容を次の三つの視点で扱う。

| 視点 | 内容 | 作業 |
|---|---|---|
| 要望 | ヒアリングで得た発言を、発言者と背景付きで記録したもの | 未整理の内容を失わず記録する |
| 要求 | 要望の背景にある問題・課題を理解し、解決の方向性として構造化したもの | 具体化、抽象化、依存関係の整理を行う |
| 要件 | 実現が必要な重要項目を明確にしたもの | 機能要求または非機能要求に分類し、後続のモデルへ渡す |

要望を単なる一覧のまま終わらせない。一方で、構造化の途中にある要望を削除して根拠を失わない。

## 最低限の管理表

モデルを補助するため、次の表を作成する。図だけを唯一の正としない。

| 識別子 | 種別 | 発言者・対象 | 内容 | 根拠 | 状態 |
|---|---|---|---|---|---|
| ACT-01 | アクター | 例: 会員 | 本を探し、予約を判断する責務を持つ | 業務ヒアリング | 確認済み |
| EXT-01 | 外部システム | 例: 蔵書情報サービス | 予約可否の判断に必要な情報を提供する | 既存資料 | 仮説 |
| WISH-01 | 要望 | ACT-01 | 希望する本を短時間で見つけたい | ヒアリング | 確認済み |
| RQR-01 | 要求 | ACT-01 | 予約可否を判断できる検索結果を提供する | WISH-01の構造化 | 合意済み |
| REQ-01 | 機能要件 | ACT-01 | 予約可否を検索結果に表示する | RQR-01から導出 | 合意済み |

`状態` は `確認済み`、`合意済み`、`仮説`、`未確認`、`今回スキップ` のいずれかで記録する。`今回スキップ` には理由と次に確認する質問を添える。非機能要件には、達成水準と評価方法も記録する。

## UMLの使い方

RDRAは、統一モデリング言語（UML）を拡張して関係を表現する。この段階では、RDRAのコンテキストモデルと要求モデルを正とし、標準UMLのユースケース図で置き換えない。

| 目的 | RDRAのモデル | UMLとの関係 | 注意点 |
|---|---|---|---|
| 目的・役割、アクター、外部システムを関係付ける | コンテキストモデル | UMLのアクター記法や関係を利用できる | ユースケースを置かない。後続のUCを先に決めない。 |
| アクターの要望から要件を構造化する | 要求モデル | RDRAの関係ダイアグラムとして表す | 要望、要求、要件の区別と発言者との対応を失わない。 |
| システムとの接点を詳細化する | 後続のシステム境界・UC | 標準UMLのユースケース図を補助的に使う | `REQ-*` と `UC-*` の対応は追跡表に記録する。 |

## 確認すること

- システムの目的・役割を一文で説明できるか。
- 対象スコープ内のアクターと外部システムに漏れがないか。
- 各アクターの責務、または責務が未確定である理由を記録したか。
- 各要望・要求・要件に、発言者または根拠があるか。
- 各要件を機能要求または非機能要求に分類したか。
- 要件と後続のBUC・UCを対応付けられるか。
- 相反する要求、同じ要求を共有するアクター、優先度が未確定の要求を明示したか。

## 避けること

- 利用者だけをアクターにして、影響力や要求決定権を持つ役割を漏らすこと。
- 個人の全件一覧と役割の網羅を混同すること。
- 「AIを使う」「検索画面を作る」だけを要望・要求・要件として記述すること。必要な場合は、実現制約または後続のUCとして別に記録する。
- 要望の原文を捨てて、構造化の根拠を失うこと。
- 標準UMLのユースケース図だけでコンテキストモデルまたは要求モデルを代替すること。
