# LLMプロジェクトの段階別判断基準

## 目的

大規模言語モデル（LLM）または検索拡張生成（RAG）を用いるプロジェクトについて、各段階の作業、成果物、次の段階へ進む条件を具体化する。RAGは、利用者の問いに応じて外部の情報源を検索し、取得した情報を根拠としてLLMが回答する構成を指す。

## 6段階と判断の境界

| 段階 | 確認する問い | 主な成果物 | 次へ進む条件 |
| --- | --- | --- | --- |
| 0. 業務要件の定義 | 誰のどの業務を、どのように改善するか | 対象業務、利用者、成功指標、許容できない失敗 | 成功と失敗を観察可能な形で説明できる |
| 1. 実データと問いの収集 | 現場の情報だけで必要な回答を作れるか | 代表データ一覧、質問例、期待回答、根拠箇所 | 主要な利用場面を代表する実例がある |
| 2. 既存アプリでの価値検証 | 情報源に基づく回答が業務で役立つか | 試行記録、不足情報、業務担当者の判定 | 価値仮説と情報源の課題を説明できる |
| 3. 評価データセットの作成 | 改善と悪化を同じ条件で比較できるか | 評価例、出自、採点基準、データ区分 | 重要な通常例、失敗例、境界条件を測定できる |
| 4. 最小構成の実装と測定 | 単純な構成で、どこまで要件を満たすか | 構成記録、評価結果、費用、応答時間 | 次の変更が必要な根拠を失敗例から説明できる |
| 5. 小規模運用 | 実際の利用状況でも価値と安全性が保たれるか | 利用ログ、失敗記録、更新した評価例 | 拡大、継続、再設計、中止を根拠付きで判断できる |

段階の番号は実施順を表す。前の段階に戻ることは失敗ではない。新しい失敗から、業務要件、情報源、評価例の不足が判明した場合は、対応する段階へ戻って成果物を更新する。

## 段階0: 業務要件の定義

### 確認項目

- 利用者は誰か。
- 利用者は現在、どのように業務を完了しているか。
- LLMを使うことで、利用者または組織にどのような変化を期待するか。
- 誤答、回答不能、遅延、停止、情報漏えいが起きた場合に、誰へどのような影響があるか。
- LLMを使わない方法を含め、比較対象は何か。

### 成果物

少なくとも、次の項目を一つのプロジェクト定義として記録する。

- 対象業務
- 利用者
- 現在の方法
- 期待する成果
- 業務上の指標と目標値
- システムの指標と目標値
- 許容できない失敗
- データ取扱いの制約
- 検証期限と責任者

業務上の指標とシステムの指標を混同しない。例えば、回答の正しさが向上すれば業務時間が短縮するという関係は、確認するまでは仮説として扱う。

## 段階1: 実データと実際の問いの収集

### データの選び方

頻繁に参照される標準的なデータだけでなく、次の違いを含める。

- 文書形式、長さ、構造の違い
- 新旧の版
- 表記ゆれ
- 複数の文書にまたがる情報
- 矛盾、欠落、誤記
- 閲覧権限の違い

検索対象となるデータそのものを合成データへ置き換えない。実データを利用できない場合は、利用できない理由と、代替データでは確認できない性質を明記する。

### 問いの記録項目

| 項目 | 内容 |
| --- | --- |
| 問い | 利用者が実際に使う表現 |
| 利用場面 | 問いが発生する業務と時点 |
| 期待回答 | 業務上必要な内容 |
| 根拠箇所 | 期待回答を裏付ける情報源と位置 |
| 重要度 | 間違えた場合の影響 |
| 発生頻度 | 確認できる場合の実測値。確認できなければ未確認と記録する |
| 出自 | 問い合わせ履歴、聞き取り、観察、合成など |

## 段階2: 既存アプリでの価値検証

### 実施前の確認

- 対象データを外部サービスへ登録できるか。
- 入力データと出力データがサービス提供者の学習に使われるか。
- データの保持期間、保存地域、削除方法は要件を満たすか。
- 利用者ごとの権限を再現できない場合、どのデータだけで試すか。

一つでも不明な事項があり、機密情報へ影響する場合は、データを登録しない。匿名化または公開情報による代替が、検証したい性質を保つかを先に確認する。

### 確認できること

- 手元の情報源だけで必要な回答が成立するか。
- 根拠を確認できる回答が業務で役立つか。
- 不足、陳腐化、矛盾している情報源は何か。
- 利用者がどのような問い方をするか。

### 確認できないこと

- 独自実装の検索精度
- 文書の分割方法と索引方式の適否
- 本番の権限制御
- 本番の応答時間、費用、可用性、監査性
- 採用するモデルと検索基盤による最終的な回答品質

既存アプリで良い結果が出た場合は、「価値仮説と情報源に可能性がある」と判断する。「独自RAGの性能が確認できた」とは判断しない。

## 段階3: 評価データセットの作成

### 構成

評価データセットは、少なくとも次の区分を識別できるようにする。

- 実際の問いと合成した問い
- 通常例、既知の失敗、境界条件
- 情報源に答えがある問いと、答えがない問い
- 単一の情報源で答えられる問いと、複数の情報源が必要な問い
- 重大な失敗につながる問いと、影響が限定的な問い

初回は、実際の失敗を含む20〜50件程度の小さな評価データセットを、作業開始の目安にできる。この件数は完成条件ではない。対象業務の種類、失敗の種類、必要な統計的確かさに応じて増やす。

### 合成データの利用条件

合成データは、次の目的に限定する。

- 実際の問いの言い換えを増やす。
- まれだが重大な条件を加える。
- 答えがない問いや、対象外の問いを加える。
- 文書形式や問い方の境界条件を加える。

合成データだけから発生頻度を推定しない。合成した問いと期待回答は、業務担当者が根拠箇所とともに確認する。生成に使ったモデルと、評価対象のモデルが同じ場合は、表現や判断の偏りが共有される可能性を未確認のリスクとして記録する。

## 段階4: 最小構成の実装と測定

### 最小構成の固定項目

- モデルと版
- システム指示とプロンプト
- 生成設定
- 検索対象データと版
- 文書の分割方法
- 検索方法と取得件数
- 外部ツール
- 試行回数
- 実行日

変更した項目を記録しない比較は行わない。複数の項目を同時に変更した場合は、結果が変化した原因を特定できないことを明記する。

### RAGの評価単位

| 評価単位 | 確認する内容 | 記録例 |
| --- | --- | --- |
| 検索 | 必要な根拠を取得できたか | 必要な根拠が上位何件に含まれたか |
| 回答生成 | 取得した根拠に従って回答したか | 正しさ、根拠との一致、不要な断定、回答不能の判断 |
| システム全体 | 利用者の業務を完了できたか | 完了率、所要時間、やり直し、担当者の判定 |
| 運用 | 制約の範囲で実行できたか | 応答時間、費用、失敗率、権限違反 |

平均値だけで判断しない。データ区分ごとの結果と、代表的な失敗例を確認する。重大な失敗は、平均値へ埋め込まず個別に示す。

## 段階5: 小規模運用と評価の更新

### 運用範囲

- 利用者、対象業務、期間を限定する。
- 人間による確認が必要な出力を明記する。
- 問題が起きた場合の停止条件と連絡先を決める。
- 記録するログと、記録してはならない情報を決める。

### 評価データセットの更新

次の事象を新しい評価例の候補にする。

- 利用者が回答を採用しなかった。
- 必要な情報を検索できなかった。
- 根拠は取得できたが、回答が根拠と一致しなかった。
- 答えがないにもかかわらず、回答を作った。
- 権限外の情報を取得または表示した。
- 応答時間または費用が許容範囲を超えた。

新しい評価例を追加した場合は、追加理由、出自、重要度、期待する挙動を記録する。評価方法を変更した場合は、変更前後の数値を同じ系列として比較しない。

## 計画を止める条件

次のいずれかに該当する場合は、実装を当然の次工程とせず、対象業務または計画を見直す。

- 対象業務と利用者を特定できない。
- 期待する成果を観察または測定できない。
- 必要な実データを正当な方法で利用できない。
- 情報源に必要な答えが含まれていない。
- 既存アプリで業務上の価値を確認できない。
- 許容できない失敗を検出または抑止する方法がない。
- 運用責任者が決まっていない。
