# ドメインと外部との境界

ドメインモデルを、通信形式や保存形式の都合から切り離す。
この文書は、直列化、永続化、読み取りの分離を扱う。集約内部の整合性は
[aggregate-consistency.md](aggregate-consistency.md)で扱う。

## 1. ドメイン型と転送用の型を分ける

境界を越えるデータは、転送用の型として別に定義する。

| | ドメイン型 | 転送用の型 |
| --- | --- | --- |
| 目的 | 業務規則の表現 | 境界を越えるための取り決め |
| 構成 | 制約付きの値、判別可能な共用体 | 基本型だけの単純な構造 |
| 変更 | ドメインの理解に応じて変えてよい | 相手が存在するため互換性を壊せない |
| 付加情報 | 直列化の属性を持たせない | 直列化の属性を持ってよい |

ドメイン型に直列化の属性や永続化基盤の基底型を持ち込まない。
ドメイン型が、通信形式と保存形式の都合で歪む。

## 2. 変換の方向で失敗の有無が変わる

ドメイン型から転送用の型への変換は常に成功する。
転送用の型からドメイン型への変換は、検証を伴うため失敗し得る。
戻り値の型でこの違いを表す。

```ts
type OrderDto = Readonly<{
  orderId: string;
  quantity: number;
}>;

const toDto = (order: Order): OrderDto => ({
  orderId: order.id.value,
  quantity: order.quantity.value,
});

const fromDto = (dto: OrderDto): Result<Order, readonly ValidationError[]> =>
  // 単一値のスマートコンストラクタを通す
  buildOrder(dto);
```

復元時に検証を省略しない。保存済みのデータが常に現在の不変条件を
満たしているとは限らない。不変条件を変更した場合は、
保存済みデータの移行または再検証が必要かを確認する。

## 3. スキーマ定義を境界の検証に使う

zodやPydanticのスキーマは、転送用の型の定義と、ドメイン型への変換時の検証を
同時に担う。スキーマから型を導出し、手書きの型定義と二重管理にしない。

```ts
const OrderDtoSchema = z.object({
  orderId: z.string(),
  quantity: z.number(),
});

type OrderDto = z.infer<typeof OrderDtoSchema>;
```

検証の失敗は想定内である。例外を送出する`parse`ではなく、
結果を返す`safeParse`を使い、ユースケースのエラー型へ変換する。

Pydanticは検証の失敗を例外として送出する。境界で捕捉し、
明示的な戻り値へ変換してからドメインへ渡す。ドメインの内部へ
`ValidationError`を伝播させない。

スキーマが検証するのは、構造と単一値の制約までである。
複数フィールドの関係や、他の集約の状態に依存する規則は、
スキーマの後段でドメインの生成関数が検証する。

## 4. 判別可能な共用体の変換方法を決める

共用体を転送用の型に落とすときは、判別子を含む平坦な構造にする。
言語固有の直列化方式を使うと、境界の両側で同じ言語を使う制約が生じる。

## 5. 転送用の型は取り決めとして扱う

フィールドの追加、削除、改名は相手を壊す可能性がある。
複数の版を並存させる方法を、変更前に決める。

## 6. 入出力を端に寄せる

ワークフローの内部に入出力を混ぜない。
必要なデータを先に読み、純粋に計算し、結果を後から書く。

```
[読み込み]  →  [ドメインの計算]  →  [書き込み]
```

計算の途中で永続化層を呼ぶと、ドメインの検証に外部環境が必要になる。
途中で外部の情報が必要な場合は、依存関数として注入する
（`type-guidelines`の`references/usecase.md`を参照）。

## 7. 更新と読み取りを分ける

更新のための型と、読み取りのための型を分ける。
画面に同時に表示するという理由で集約を大きくしない。
表示の都合を更新の設計へ持ち込むと、競合と性能の問題が生じる。

## 8. 境界づけられたコンテキストは自身の保存領域を持つ

他のコンテキストの保存領域を直接読み書きしない。
一方の変更が他方を壊す。連携はドメインイベントまたは公開された関数で行う。

## レビュー項目

- ドメイン型に直列化または永続化基盤の都合が現れていないか。
- 転送用の型からドメイン型への変換で、検証を省略していないか。
- スキーマの定義と、転送用の型の定義が二重管理になっていないか。
- 検証の失敗が例外として送出される場合、境界で明示的な戻り値へ変換しているか。
- スキーマが検証しない規則（複数フィールドの関係、外部状態への依存）を、
  後段のドメインの生成関数が検証しているか。
- 保存済みデータの復元経路が、未検証の値を検証済みとして扱っていないか。
- 転送用の型を変更したとき、相手側の互換性を確認しているか。
- ドメインの計算処理の途中で、入出力を行っていないか。
- 表示の都合で集約の範囲を広げていないか。
- 他のコンテキストの保存領域を直接参照していないか。

## 型だけでは保証できない範囲

変換処理を通さない経路の存在、保存済みデータの実際の妥当性、
相手側の実装が取り決めに従っているかは、型では保証しない。
生成経路の限定、移行時の再検証、境界での検査で保証する。
