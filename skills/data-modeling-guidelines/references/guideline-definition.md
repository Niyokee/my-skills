# データモデリング・データベース設計指針の策定

## 目的

設計指針は、好みを統一する文書ではない。繰り返し起きる設計判断について、守る業務上または運用上の性質、判断条件、例外、確認方法を共有する。

## 策定手順

1. 指針の利用者、対象システム、対象データ、設計段階、対象外を決める。
2. 既存のモデル、スキーマ、障害、移行、レビュー指摘から、繰り返し発生する判断を集める。
3. 各候補について、守る性質と、違反時に起こる不正な状態を記録する。
4. 必須規則、条件付き規則、推奨、禁止、参考例を区別する。
5. 概念データモデル、論理設計、物理設計、実装、運用のどこで適用するか決める。
6. 自動検査、レビュー、計測、運用監査のどれで確認するか決める。
7. 既存システムで適用できない場合の例外申請、期限、代替策、再確認日を決める。
8. 実際の設計例へ適用し、判断できない表現と過剰な規則を修正する。

## 規則の書式

各規則を次の形で記録する。

| 項目 | 内容 |
| --- | --- |
| 識別子 | 安定した規則番号 |
| 題名 | 一つの判断を表す名前 |
| 適用条件 | 対象となる設計段階、データ、状況 |
| 守る性質 | 完全性、整合性、履歴、性能、可用性など |
| 必須事項 | 実施しなければならない内容 |
| 禁止事項 | 許されない状態または方式 |
| 理由 | 違反時に生じる不正な状態と影響 |
| 例外 | 例外を認める条件、承認者、期限、代替策 |
| 確認方法 | 自動検査、レビュー項目、計測、証拠 |
| 例 | 適合例と不適合例 |
| 関係する規則 | 前提、競合、優先順位 |

「適切に設計する」「必要に応じて索引を付ける」のように判定できない文を書かない。対象、判断基準、必要な証拠、期待する結果を明記する。

## 最低限扱う論点

対象に関係するものだけを採用する。

- 業務語彙、命名、同義語、名称変更
- 業務上の同一性、代理キー、一意性
- 必須、任意、不存在、未知、未決定、適用外
- 一対多、多対多、複数要素へ依存する事実
- 分類、役割、状態、期間、履歴、訂正
- 多値、導出値、重複保持、正とするデータ
- 参照整合性、削除、統合、番号変更
- 制約を保証するデータベース、アプリケーション、運用の分担
- トランザクション、競合、再試行、重複、照合
- データ量、処理量、索引、分割、保管
- 個人情報、機密区分、監査、削除
- スキーマ変更、移行、後方互換性、切り戻し

## 既存文書との整合

既存の命名規則、アーキテクチャ決定記録、セキュリティ基準、運用基準と競合する場合は、優先順位を明記する。同じ規則を複数文書へ複製せず、正とする文書と参照関係を決める。

## 完了条件

- 各規則に適用条件、理由、違反状態、確認方法がある。
- 必須、推奨、禁止、例外が区別されている。
- 概念データモデル、論理データベース設計、物理データベース設計、実装、運用の責任範囲が区別されている。
- 少なくとも一つの実例と一つの反例へ適用済みである。
- 例外の承認者、期限、代替策、再確認方法が定義されている。
